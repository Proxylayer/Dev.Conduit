Dev.Conduit — Technical Architecture

Dev.Conduit runs on a machine that can reach a restricted endpoint and lets a developer drive that machine's network access from a workstation that cannot, either through a browser console or by relaying the application's existing traffic unchanged.

Scope: one ASP.NET Core project, two modesTarget framework net10.0-windowsCompanion: README.md, docs/ROUTING.md, docs/LOCAL-MODE.md

00   What it is and what problem it solves

A developer needs to call an internal service — say the SOAP endpoint at http://10.0.0.5:8080/services/orders/service.svr. Their laptop has no route to 10.0.0.5: it sits behind a VPN boundary, an allowlist, or a network segment the workstation is not on. Some other machine does have that route. Dev.Conduit is what you run on that machine.

Once it is running there, the developer has two ways to reach the endpoint, and they solve two different problems:

SurfaceWhat it is forHow the request is composed
The console
/ and /api		 Exploration. Poking at an endpoint by hand, reading the exact response, replaying it. In the browser, as a JSON description of a request. The server builds and executes the real call.
Transparent forwarding
/route		 Running the application. Code that already calls an address keeps calling it. By the caller, as an ordinary HTTP request. Dev.Conduit relays verb, path, query, headers and body without altering them.
The mental model. Closest previous-technology analogy: a desktop REST client such as Postman, except that the outbound call originates on the host running the service rather than on the workstation holding the browser. The analogy is approximate — there is no collection format, no environment substitution and no scripting — and it covers only the console half. The /route half has no Postman equivalent; it is an authenticated HTTP relay.

The tool is one ASP.NET Core project, src/Proxylayer.DevConduit, targeting net10.0-windows, with a browser console built from plain HTML, CSS and JavaScript served out of wwwroot, and a Windows Forms tray app in the same exe. There is no Node.js, no npm and no client build step. The same executable runs in two modes — server on the privileged machine, local on the workstation — chosen by DevConduit:Mode or the --mode argument. Keeping both roles in one binary is deliberate: the wire contract between the two ends cannot drift, because both ends are compiled from the same source.

Composition and the request pipeline

Program.cs only chooses a launch path, through ServiceLaunch.Resolve: tray starts the tray app and service-admin its elevated helper; the Windows service lifecycle verbs and a start by the service control manager go to the service host (see 03.4); everything else runs in the console. The console, the service and the tray's in-process local mode all build the application through DevConduitApplication.TryBuild, which is where the composition below lives, including the checks that refuse to start and their exit code. Its first step layers the machine and user settings files into configuration (see 03.3); a file that cannot be used is a fatal message naming it. The tray passes a log sink, which replaces every other log provider, since a tray has no console. Mode is resolved next, before anything else is registered. DevConduitModeSelection reads --mode first, then DevConduit:Mode, defaulting to Server, and writes the resolved value back into configuration as a last-wins in-memory source so that the bound DevConduitOptions cannot disagree with the mode the process actually chose. ServerModeStartup.Register or LocalModeStartup.Register then contributes the mode-specific registrations; everything shared — storage, the forwarder, the capture recorder, the HTTP client set — is registered once for both.

Middleware order in DevConduitApplication carries two decisions worth stating explicitly:

  • /health is a terminal branch (MapDevConduitHealth) mounted first, ahead of the unconfigured-tenant notice and of UseAuthentication(). With no Entra ids the OpenID Connect options cannot be built at all, so a probe that reached authentication would fail with a 500. It answers {"status":"ok","configured":…} in both modes.
  • MapDevConduitRoute() is mounted before UseAuthorization(). The global fallback policy is cookie-only, and applying it to /route would shut out bearer callers, so the /route branch runs its own RouteAccess policy instead.
  • UseStaticFiles() is mounted after UseAuthorization(), so the fallback policy guards the console assets as well as the API. Only /health is anonymous.

/route is a terminal middleware branch (app.Map) rather than a mapped endpoint. A proxy has to accept any verb, including the custom ones legacy services define — PROPFIND, SUBMIT, whatever the upstream was written against — and a route pattern cannot express an open verb set.

01.2   The console request lifecycle

The browser never makes the outbound call. It composes a description of one, posts that description to POST /api/proxy/execute, and the server does the rest. Unlike /route, the console path buffers: ProxyExecutor sends with HttpCompletionOption.ResponseContentRead and reads the body to a byte array, because the UI needs the complete response to render it. Body size in history is capped by DevConduit:MaxStoredBodyBytes.

Failure semantics

A transport failure — DNS, TLS, refused connection, timeout, a malformed URL — still answers HTTP 200 from /api/proxy/execute, with response: null and error / errorKind populated, and is still recorded in history. The status code of that API call describes whether Dev.Conduit did its job, not whether the upstream did. This is the opposite of /route, which answers with proxy semantics.

A destination in DevConduit:BlockedEgressNetworks takes the same path, with errorKind: "Blocked" and an error naming the host, the resolved address and the setting. The console shows it as BLOCKED. See 03.2.

Reading the status. A request that failed at the transport layer shows 200 in a browser network tab. The error kind is in the response body and is surfaced in the response pane as an error callout, not as an HTTP status. Looking only at the network tab will mislead you.

The API surface

Every /api endpoint sits in one group that requires authorization and applies ClientHeaderFilter, which rejects any call not carrying X-DevConduit-Client: 1 with a 400. Combined with a SameSite=Lax session cookie this is the CSRF control: a cross-site form post or image request cannot set a custom header, so it cannot drive the API with a signed-in developer's session.

02.1   The forwarding contract: /route

/route relays a request without altering it. The verb, path, query string, body and all non-excluded headers arrive at the upstream as the caller composed them, and the upstream's status, headers and body come back untouched. The same endpoint exists in both modes; only the next hop differs.

URL translation

The upstream URI is the resolved origin, then the remaining path, then the original query string verbatim. The port lives only in the origin and is never repeated in the path. Taking the motivating case: 

Original call the application makes
  POST http://10.0.0.5:8080/services/orders/service.svr?wsdl

Header form — the path is untouched, the origin comes from a header
  POST http://localhost:8091/route/services/orders/service.svr?wsdl
  X-DevConduit-Target: http://10.0.0.5:8080

Alias form — with "Routes": { "orders": "http://10.0.0.5:8080" }
  POST http://localhost:8091/route/orders/services/orders/service.svr?wsdl
       ↵ the leading "orders" segment is consumed; the rest is the upstream path

Dev.Conduit reconstructs, either way
  http://10.0.0.5:8080/services/orders/service.svr?wsdl

Target resolution

OrderRuleResult
1 The first remaining path segment matches a route name under DevConduit:Routes, case-insensitively That segment is consumed; the alias origin is the target
2 X-DevConduit-Target names an origin Nothing is consumed; the whole path is the upstream path

A resolved origin must be an absolute http or https URI with no path, no query, no fragment and no embedded credentials; RouteOrigin.TryParse rejects each of those with its own message, and embedded credentials are refused with a pointer at X-DevConduit-Upstream-Authorization. When DevConduit:Route:AliasesOnly is true, X-DevConduit-Target is refused outright (errorKind: "aliases_only") and only aliases resolve.

Aliases are the route names under DevConduit:Routes, each a string origin or an object { "Target": origin, "Remote": name }, read once by RoutingConfigurationParser and validated once, at construction of RouteAliasTable. Server mode reads only the target and ignores the remote. A malformed entry is dropped and logged at error level with its reason; the host still starts. If AliasesOnly is true and no usable alias survives validation, startup warns that /route will refuse everything.

This is the contract. Headers are classified by RouteHeaderPolicy and applied by RouteForwarder.CopyRequestHeaders; the credential and Host headers are then written by the mode's IRouteEgress implementation — UpstreamRouteEgress in server mode, RemoteRelayRouteEgress in local mode.

Why two Authorization headers. The caller holds one credential for Dev.Conduit and, optionally, a separate one for the upstream. Neither leaks into the other's request: Dev.Conduit's token is consumed by authentication and dropped, and the upstream's credential travels under a name nothing else looks at until the last hop renames it back. A SOAP POST sent with X-DevConduit-Upstream-Authorization: Basic … reaches the upstream as Authorization: Basic …, and the upstream never sees the Entra token.
The local shared secret stops at the listener it authenticates. X-DevConduit-Local-Secret is stripped by the forward-proxy ingress and is in RouteHeaderPolicy.Control, so a request that carries it into /route does not forward it to the next hop in either mode. It is also on the default DevConduit:SecretHeaderNames list, so any residual occurrence is captured as ***redacted*** rather than in clear text.

Response direction

  • Status code and every response and content header are copied, minus the hop-by-hop set. A header Kestrel rejects is logged at information level and dropped rather than failing the response.
  • No decompression. The route client is built with AutomaticDecompression = None, so the payload arrives with whatever Content-Encoding the upstream chose and the caller receives the bytes the upstream actually sent.
  • No redirect following. AllowAutoRedirect is false, so a 3xx is relayed as a 3xx.
  • No cookie jar. UseCookies is false on every client, so Dev.Conduit never accumulates upstream state between requests.

Streaming

Neither direction is buffered. The request body is wrapped in a pass-through reader as HttpClient consumes it; the response is read with HttpCompletionOption.ResponseHeadersRead and copied to the caller in 64 KB chunks from a pooled buffer. Memory does not scale with payload size, and a large SOAP response starts arriving at the caller before the upstream has finished sending it.

The per-request timeout comes from DevConduit:Route:TimeoutSeconds (default 100, clamped to 600) and is linked to HttpContext.RequestAborted, so a caller who disconnects does not leave an upstream call running. If the response body is cut short after headers have gone out, the only honest signal left is to abort the response — pretending it completed would hand the caller a truncated body that looks whole.

Local mode offers two ingress styles on two ports. They exist because two different classes of client need routing and they cannot be addressed the same way.

Both converge on RemoteRelay, which chooses the remote, addresses it the same way and presents the same three headers, so the two ingress styles cannot drift apart in what they send or where they send it.

Ingress A — the reverse proxy

Identical URL contract to server mode: point the client at http://127.0.0.1:8092/route/… and name the upstream with an alias segment or an X-DevConduit-Target header. DevConduit:Routes is read from the same configuration section server mode uses, so an alias resolves on the workstation before the call leaves it. A remote is then chosen for the resolved origin, first match wins: the remote of the route the alias segment named or whose target is the same host and port; else the first remote whose Targets rule matches; else DevConduit:DefaultRemote, which defaults to the only remote when there is one. With several remotes, no default and nothing claiming the origin, the answer is 400 with errorKind: "no_remote". The request is then rewritten to {remote endpoint}/route{remaining path}{query} and relayed with a token for that remote's identity and scopes; a capture records the remote as an X-DevConduit-Remote header item. Bodies stream in both directions exactly as in server mode — it is the same RouteForwarder, with a different IRouteEgress behind it.

A 401 or 403 raised by the remote instance is about this machine's token, not about the upstream, and relaying it verbatim would send a developer looking at the wrong end of the chain. Local mode preserves the status code and replaces the body with one that names what to fix. The two are told apart by the shape of the refusal rather than by status alone: Dev.Conduit challenges with an empty bearer 401, and refuses with a small JSON body naming one of its own error kinds. Detection buffers at most 8 KB and only for a JSON content type, so a large upstream payload is never held in memory. An upstream's own 401 or 403, relayed through the remote, arrives untouched.

Ingress B — the forward proxy

Set HTTP_PROXY=http://127.0.0.1:8093 and change nothing else. This is the option for a client that has no notion of a base URL you can rewrite.

Why this is not Kestrel. A forward proxy is addressed with the absolute-form request target — GET http://host:port/path HTTP/1.1 — and must accept the CONNECT verb. Kestrel hands an application neither. The listener is therefore a raw TcpListener with its own request-head parser, bound to the same loopback address the reverse proxy uses, and it never runs in server mode.

Per request, the listener decides exactly one thing: does the host match a forward-proxy rule — a route origin or a remote's Targets? A match is relayed to that rule's remote, a route winning over a Targets rule exactly as on /route; there is no default-remote fallback here.

That guard is what stops HTTP_PROXY pointing at this process from folding it into itself. The relay's own HttpClient is separately configured with UseProxy = false for the same reason — a developer running local mode has very likely set HTTP_PROXY in the environment this process itself inherits.

The loopback constraint

Local mode performs no inbound authentication. That absence is exactly what buys zero application changes — and it means loopback is the only boundary keeping the developer's Entra token out of reach of anything off the machine. The constraint is therefore enforced twice, on purpose:

  • LocalModeStartup.Validate runs before anything binds, and refuses to start when BindAddress is not a loopback address, when DevConduit:Remotes is empty or an endpoint is not an absolute http/https URI, when a route or DevConduit:DefaultRemote names an unknown remote, when several remotes and no default leave a route with nowhere to go, or when the two ports are invalid or identical. Each problem is printed with the setting name and why it matters, and the process exits non-zero.
  • LocalModeStartup binds Kestrel in code to BindAddress:Port and swaps in an empty Kestrel configuration loader, so no Kestrel:Endpoints entry from configuration (the UAT https endpoint on 0.0.0.0, for one) can open a second, off-loopback listener. Ignored endpoints are logged at startup.
  • ForwardProxyServer.StartAsync re-resolves the bind address and throws if it is not loopback, so no code path can bring the raw listener up off-loopback even if the first check were bypassed.

A remote whose effective TenantId or ClientId is missing is deliberately not fatal. The host starts, serves the console and logs a warning naming the remote; each request relayed to it then fails with a message naming the settings. That lets a developer bring local mode up and read the startup banner before touching the app registration.

02.3   Authentication

The console session: authorization code, PKCE, response_mode=query

Server mode registers two schemes: AddMicrosoftIdentityWebAppAuthentication for interactive sign-in and a cookie session afterwards, and AddMicrosoftIdentityWebApiAuthentication for bearer validation on /route. Registering the API scheme second makes it the default, which is wrong for every endpoint except /route, so the defaults are put back explicitly: cookie for authenticate and sign-in, OpenID Connect for challenge and sign-out. Without that, the console would answer 401 instead of redirecting to Entra.

The OIDC handler is then post-configured with ResponseType = code, ResponseMode = query, UsePkce = true and SaveTokens = false, and the correlation and nonce cookies are pinned to SameSite=Lax with SecurePolicy = SameAsRequest.

Why response_mode=query is load-bearing. The library default is form_post. That makes the authorization response a cross-site POST from login.microsoftonline.com back to the callback, which means the correlation and nonce cookies must be SameSite=None to survive the round trip — and browsers only accept SameSite=None on cookies also marked Secure, which a plain-http localhost listener cannot set. The result is a sign-in that loops back to the login page with no useful error. Switching to query makes the callback a top-level GET navigation, which SameSite=Lax permits, so the flow completes over plain http on localhost. The trade is that the authorization code flow requires a client credential. Here that is a federated managed identity assertion, with a client secret supported only as a fallback; see the client credential below.

The session cookie is named DevConduit.Auth, is HttpOnly, SameSite=Lax, SecurePolicy = SameAsRequest, sliding, with a 10-hour lifetime.

Admission control on /route

RouteAuthorizer tries the bearer scheme first, because that is how programmatic callers arrive, and falls back to the cookie session so a signed-in developer can exercise the endpoint by hand from the browser or from curl with a session cookie. Both are then held to the same RouteAccess policy, which carries the same AllowedUserOids / AllowedGroupIds allow-list rules as the global policy but accepts either scheme.

Token acquisition in local mode

MsalDevConduitTokenProvider signs in as a person, not a service principal, because routed history on the remote instance is attributed to whoever the token belongs to. Each remote's identity is its own TenantId and ClientId, inherited from AzureAd when absent, and its scopes default to api://{ClientId}/DevConduit.Forward. The provider keeps one MSAL public client per distinct tenant and client id pair, and every request uses the token for its remote's identity and scopes.

  1. Silent, against the encrypted on-disk cache. Instant and silent when a cached token exists.
  2. Interactive browser sign-in, when InteractiveFallback is true and the process is interactive. The browser opens against http://localhost, which the app registration must list as a Mobile and desktop applications redirect URI.
  3. Device code, when interactive sign-in is disabled or unavailable. The code and URL are logged at warning level so they are visible in a console or a CI log.

The token is held in memory and reused until five minutes before expiry, and persisted to {CacheDirectory}\devconduit.msal.cache, DPAPI-protected on Windows. Every public client is registered with one shared MsalCacheHelper over that one file; MSAL keeps each client id's entries apart inside it. A developer signs in once per identity per machine, not once per process. Acquisition, for every identity, is serialised behind one semaphore: a cold start with ten parallel calls opens one sign-in prompt rather than ten, and two clients never write the shared file at once. If the cache cannot be opened, local mode logs a warning and continues with an in-memory cache — an extra sign-in, not a failed request.

LocalTokenWarmup acquires a token for each distinct identity during host startup rather than on the first proxied call, so each app registration asks for at most one sign-in there. Deferring it would mean an application appearing to hang on its first request while a browser window opens behind it, with nothing on screen explaining the wait. If that startup sign-in fails the host keeps running: the console stays reachable, the error is visible in one place, and each relayed request reports the same failure with its own context.

The local-mode principal

LocalModeAuthenticationHandler authenticates every request as one fixed pseudo-user, local, carrying an object-identifier claim of the same value. This is not a security control — the boundary is the loopback bind — but it gives the console, the /api surface and the storage layer a stable principal to work against instead of forcing them to handle anonymity. local is also a valid storage path segment under the same rules a real oid is checked by.

02.4   Certificates, /cert, export and import

A server with a host name owns its TLS certificate. It creates, stores and rotates it itself; nothing about certificates appears in settings. The host name is DevConduit:Server:Hostname, or, when that is blank and the process is the service or runs beside the installed service (the rule DataRootDefault applies), this computer's DNS name: ServerHostnameDefault takes IPGlobalProperties' host and domain names when there is a primary DNS suffix or domain, else Environment.MachineName, lower-cased and checked with DnsHostname. The export command, the tray's console link, its export and the Server page (which shows the default greyed and never writes it) all see the same effective name. A client learns everything it needs — host name, address, port, Entra ids, routes, the server certificates to trust, and a client certificate — from one file the server exports, <hostname>.conduit, and keeps it current through an internal endpoint, /cert.

/cert and mutual TLS

GET /cert answers { hostname, serverCertificates: [ { der, notBefore, notAfter, thumbprint } ], clientCertificate: { notAfter, serial, renewAfter } }; POST /cert/renew takes { csr }, a PKCS#10 request for a new P-256 key under the enrollment's subject, and answers the new certificate. Both are mapped only in server mode with the managed endpoint, outside Entra sign-in, outside the /api group, the routed capture and any listing, behind a per-address fixed-window rate limit, and log almost nothing.

The HTTPS endpoint uses ClientCertificateMode.DelayCertificate: the handshake never requests a client certificate, so a browser opening the console is never prompted. The /cert handler calls GetClientCertificateAsync(), which asks for it then — TLS 1.3 post-handshake authentication or TLS 1.2 renegotiation, both HTTP/1.1 only — and the renewal reads its body first, since renegotiation cannot start with request data in flight. Kestrel's own chain check is switched off; ClientCertificateValidator builds an X509Chain with CustomRootTrust holding only the client authority, requires client authentication and the validity period, reads the enrollment from the subject, and requires the serial to be in issued.json under that enrollment, which must not be revoked. Anything else is a bare 401 or 403.

A renewal is checked again inside ServerCertificateAuthority.Renew, under the store's lock: the presented certificate must still be accepted (403), have fewer than 60 days left by ClientCertificateRenewal.IsDue, the rule the client uses (409), and the request must name exactly the enrollment's subject (400). The new certificate joins the enrollment; the presented one is marked superseded and stays valid, for GET /cert and for another renewal in its own window, until it expires. Several users of one workstation renew from the same machine identity, so one certificate may legitimately renew more than once; revoking the enrollment (certs revoke <serial> or certs revoke --enrollment <id>) is what ends them all. certs list groups by enrollment, each with its latest certificate.

Export and import

export (elevated, or the helper's service-admin export) checks the output path first — a .conduit name in an existing folder, not a folder or a link — then converges the certificates, creates an enrollment and its client certificate, and writes { format: "dev-conduit/1", hostname, address, port, remote, tenantId, clientId, routes, serverCertificates, clientCertificate, exportedAt } (an import also accepts poc-devproxy/1, the same schema in a .proxyconfig file exported by POC.DevProxy) with an access list of the exporting account and Administrators, through a temporary file in the target folder moved into place. The client certificate travels with its private key, so the file is a secret — but one with narrow reach: it authenticates only to /cert, which hands out public certificates and renews within the last 60 days of a certificate, in its enrollment. /route and the console still need Entra ID.

The pure parts — the document and its validation, the hosts-file text edit, the settings merge, pin merging, the rotation decision — are kept apart from the I/O. Nothing in it depends on an interactive user, so the MSI runs the same import <file> --machine as LocalSystem during a Workstation install given CONDUITCONFIG.

The hosts file is edited byte for byte (HostsFile, HostsFileText): it is read as bytes, a UTF-8 byte order mark is kept aside, and the rest is decoded as ISO-8859-1 so every byte maps to one character and back; each line keeps its own CRLF or LF ending, the managed line takes the file's dominant ending and is ASCII only, and whether the file ended with a line ending is kept, so adding and removing the line restores the original bytes. The file is replaced through File.Replace, which keeps its access list, with retries while another process holds it.

On append, the entry file is written first, its summary is inserted at the head of the index, the index is rewritten, and only then are the pruned entries' files deleted — so a crash mid-append leaves an orphaned file, never a dangling index row. Atomic writes

AtomicJsonFile.WriteAsync serialises to {path}.tmp, flushes, then moves it over the target with overwrite: true. A reader never observes a half-written file, and a crash cannot leave one behind. Every write for a given user and scope is serialised on that user's semaphore, so two concurrent requests cannot interleave read-modify-write cycles on the same index.

Capped tee capture

CappedBuffer retains the first N bytes handed to it and counts the rest: once the cap is reached it stops retaining, sets a truncation flag, and keeps counting. CapturingReadStream wraps the inbound body and appends what it sees as the outbound call consumes it; the response copy loop appends each chunk after it is written to the caller.

The invariant. Capture is strictly an observer. It can be truncated, it can be dropped from the write queue, and it can fail entirely — none of which changes a single byte of what the caller receives, and none of which can fail the caller's request. CapturingReadStream does not even dispose the stream it wraps: that stream belongs to the request pipeline, not to the observer.

03.2   Security posture

These are trade-offs, stated as trade-offs. Read this section before running the tool anywhere but your own machine.

What the tool is

This is an authenticated arbitrary-request relay, by design. It executes outbound HTTP requests of the caller's choosing, from this machine, with this machine's network access. That is the purpose and also the principal risk: anyone who can reach it and authenticate can reach whatever it can reach — internal services and management interfaces among them. Authentication narrows who; it does not narrow where. There is no egress allow list beyond AliasesOnly, which restricts /route only and does nothing to the console. The one fixed exception is the deny list below, which keeps the cloud metadata endpoints out of reach.

In server mode the mitigation is the bind address. With no Kestrel endpoint and no urls configured it listens on http://localhost:8091; exposing it off-box takes an explicit endpoint, and any plain http listener beyond loopback logs a prominent warning, because tokens and proxied traffic would cross the network unencrypted. In local mode there is no such option: a non-loopback bind is a fatal startup error, and configured Kestrel endpoints are ignored.

The cloud metadata egress block

The VM's managed identity is one request away. The UAMI that backs the app registration's credential is attached to the VM, and any process on the VM can ask the instance metadata service for its token at http://169.254.169.254/metadata/identity/oauth2/token. Dev.Conduit is a process on the VM that sends requests of the caller's choosing. Without a block, any signed-in user could compose that request in the console and read the app's credential out of the response.

EgressNetworkGuard therefore refuses connections to the networks in DevConduit:BlockedEgressNetworks. The defaults are 169.254.0.0/16 (IPv4 link-local, including the metadata service), 168.63.129.16/32 (the Azure WireServer) and fe80::/10 (IPv6 link-local). The configuration binder appends configured entries to the defaults, as it does for SecretHeaderNames, so configuration can add networks but never remove one. Malformed entries are logged at startup and ignored.

The local hop is deliberately unauthenticated

The trade being made. Requiring a credential on the local hop would put a token back into the application that local mode exists to keep it out of — and that credential would have to be provisioned into the Angular dev server, the Java client and the legacy executable, which is precisely the code change the design is buying its way out of. So the local hop authenticates nothing, and loopback is the boundary. Every process on the workstation can reach it; nothing off the workstation can.

DevConduit:Local:SharedSecret narrows that to the processes a developer chose to tell, via X-DevConduit-Local-Secret, compared in fixed time. It applies to /route and to the forward proxy — the paths that carry application traffic — and deliberately not to the console UI or the /api surface, which stay reachable so the tool remains usable; a browser cannot attach a custom header to its own navigation. Unset, which is the default, means loopback is the only control.

No TLS interception, and no certificate authority

A CONNECT to a host matching a target rule is refused with 502 and a body that teaches rather than merely refuses. Rewriting an HTTPS request would mean terminating TLS on the workstation and presenting a certificate for a host Dev.Conduit does not own. Minting that certificate is the easy part; getting it trusted is the part that does not scale and carries the risk.

03.3   Configuration reference

Layering, and the settings files that survive an update

An update extracts a new zip over the folder and so replaces every appsettings*.json. Settings for one machine or one person live in two optional files that no update touches. SettingsFiles owns their paths and inserts them directly after appsettings.{Environment}.json, so the order a launch reads, each source winning over the ones before it, is:

#SourceRead by
1appsettings.jsonevery launch
2appsettings.{Environment}.jsonevery launch
3%ProgramData%\Proxylayer\Dev.Conduit\settings.json, machine settingsevery launch: console, tray and service
4%LOCALAPPDATA%\Proxylayer\Dev.Conduit\settings.json, user settingsconsole and tray; never the service, which runs as LocalSystem for every user
5user secretsDevelopment only
6environment variables, then the command lineevery launch; the service passes no command line

Both files are optional; an absent or blank one adds nothing, and one that is not a JSON object stops startup with a message naming it. The tray's setup window is the only writer the tool provides, and it never edits an appsettings file. SettingsChangeSet describes a change as configuration paths to set (a value, or a whole section) and paths to remove; SettingsFileWriter applies one to a JsonNode document, leaving every other key as it was, and replaces the file through a temporary file beside it.

The machine file is checked before it is read. The service reads it as LocalSystem, and ordinary users can create files in a folder under %ProgramData%, so a file planted before an administrator first saved one would reconfigure the service. MachineSettingsAccess refuses, in every launch, a file owned by anyone but Administrators, SYSTEM or TrustedInstaller, or with an allow entry granting anyone else write access. The elevated helper creates the file with a protected access list: Administrators and SYSTEM full control, Users read.

Configuration merges sources key by key and has no way to delete a key a lower source defines. The window therefore writes DevConduit:Remotes and DevConduit:Routes as whole sections holding only the entries that differ from the layers below; an inherited entry is switched off with "Enabled": false, which RoutingConfigurationParser treats as absent. Lists merge by index, so a list written over a longer inherited one is padded with blank entries, which every reader of those lists drops. A value equal to the inherited one is removed rather than written, so a later appsettings.json still reaches it.

Build, test, publish

Three PowerShell 7 scripts at the repository root, each with the same three modes: quiet by default, -Detailed for full diagnostic output, -Target to narrow to one project or one set of tests.

test.ps1 runs the Microsoft.Testing.Platform executable directly with --no-ansi --progress off: headless by construction, no watch mode, no UI, and a non-zero exit on failure. deploy.ps1 is a framework-dependent publish — a console application with no IIS site and no remote copy step, which can optionally register itself as a Windows service — so the ASP.NET Core Runtime 10 and, for the tray's Windows Forms, the .NET Desktop Runtime 10 must both be present on the machine that runs it. The project targets net10.0-windows with UseWindowsForms but keeps the console subsystem (DisableWinExeOutputInference), so the console and service runs keep their console.

Startup prints a banner naming the mode, the bind address, whether the Entra token is validated or acquired, whether routed capture is on, and — in local mode — each remote with its endpoint and identity source, the default remote, each route as name -> target via remote, the forward-proxy port, the effective target rules per remote and the token cache directory. If that banner names the wrong mode, nothing else about the configuration matters yet.

Running as a Windows service

On the server the same exe runs as the Windows service Dev.Conduit through Topshelf, which handles only the lifecycle: install, uninstall, start, stop, help, and running under the service control manager. ServiceLaunch sends a launch to Topshelf when its first argument is one of those verbs, or when the process's parent is services.exe in session 0, the same parent-process test Topshelf applies. Any other command line runs in the console exactly as before. 

.\Dev.Conduit.exe install                    # elevated; LocalSystem, delayed automatic start
.\Dev.Conduit.exe start
  • The service builds the application with no command-line arguments. The service control manager starts the exe with Topshelf's -displayname and -servicename, which the configuration command-line provider would reject, so a service reads only the appsettings files and the environment.
  • The content root is the exe's folder whenever running as a service (its working directory is C:\Windows\System32) and whenever that folder is a published layout with a wwwroot, so the published exe finds its settings however it is launched. A build output folder has no wwwroot, so dotnet run keeps the project directory.
  • -environment:<name> is an optional custom install argument: after install it writes DOTNET_ENVIRONMENT=<name> into the service's Environment value under HKLM\SYSTEM\CurrentControlSet\Services\Dev.Conduit, because a service sees machine environment variables only as they were at boot. Nothing needs it: without it the service runs as Production.
  • The data root defaults to %ProgramData%\Proxylayer\Dev.Conduit in server mode when running as the service or while the service is installed (DataRootDefault, applied by DevConduitApplication and by CommandConfiguration for export and certs), so a console export finds the service's certificates; elsewhere it stays %LOCALAPPDATA%\Proxylayer\Dev.Conduit. The default is added as an in-memory source only when no layer names DevConduit:DataRoot.
  • Local mode is refused as a service: its interactive sign-in cannot be shown in session 0, so the build fails with the usual fatal exit code.
  • A service logs to the console provider and to the Application event log under source Dev.Conduit, this application's categories from Information. A failure before the host exists is written to the event log directly. Recovery restarts the service a minute after a failure and resets the count daily.

Packaging: the MSI

build.ps1 -Configuration Release also publishes the app self-contained for win-x64 and builds installer\Proxylayer.DevConduit.Installer.wixproj, a WiX v5 package (pinned to 5.0.x; v6 is not used for licensing reasons), into artifacts\Dev.Conduit-<version>.msi and a zip with INSTALL.txt. The version is <Version> in the app's project file; the MSI's product version is bound to the exe's file version, so the two cannot drift. The framework-dependent zip is still built beside it.

  • One per-machine package, two roles chosen by ROLE. Workstation adds an HKLM Run value that starts the tray for every user; the tray shows that entry as on and read-only and drops its own HKCU value when both start the same exe, since the second launch would open the first's setup window. Server installs the service through the MSI service tables rather than Topshelf's install: started by the service control manager with no arguments, the exe still finds services.exe as its parent and runs the Topshelf host under the configured name, and DOTNET_ENVIRONMENT comes from the same Environment value Topshelf's install would have written. A Workstation install may also import a server's .conduit (CONDUITCONFIG, below).
  • The service binary must be the key file of the component that installs the service, so the exe is authored in two mutually exclusive role components. Recovery uses the WiX util custom action, since the Windows Installer failure-actions table is documented not to work as expected; the delayed start uses the native MsiServiceConfig table.
  • ROLE and ENVIRONMENT are recorded under HKLM\SOFTWARE\Proxylayer\Dev.Conduit and read back on upgrade unless the command line gives them; neither has a Property-table default, because one could not be told apart from a command-line value. ENVIRONMENT, for silent installs only and defaulting to Production, is checked against the elevated helper's rule by a small .NET Framework custom action, since MSI conditions cannot match a character class.
  • CONDUITCONFIG (secure, not recorded, so an upgrade imports only when it is given again) names a .conduit (or legacy .proxyconfig) for a Workstation install: typed or picked with Browse (a DTF custom action showing a file dialog) on the Role page, or given on the command line. The immediate ValidateConduitConfig action, before the launch conditions, requires the Workstation role, a full path on a local disk, a .conduit or .proxyconfig name and an existing file, and a launch condition shows its reason. After InstallFiles a deferred, no-impersonate WixQuietExec64 action, ImportConduitConfig, runs "[INSTALLFOLDER]Dev.Conduit.exe" import "[CONDUITCONFIG]" --machine (passed as its CustomActionData) as LocalSystem, under the condition ROLE = "Workstation" AND CONDUITCONFIG AND NOT REMOVE. Its output goes to the log; a refused file returns non-zero and rolls the install back. LocalSystem is why the file must be local: it cannot read the user's shares or mapped drives.
  • The settings files and the data root live outside the install folder, so upgrade and uninstall never touch them. The Server role creates %ProgramData%\Proxylayer\Dev.Conduit with a protected access list and never removes it.
  • The package has its own UpgradeCode. POC.DevProxy, the product's previous name, is detected only: an Upgrade row for its UpgradeCode with OnlyDetect sets LEGACYPRODUCTFOUND, and a launch condition stops the install while it is set. Nothing is upgraded, removed or migrated.
  • While a product with the package's UpgradeCode is installed, in either role, installing the service is the MSI's; removing it is the MSI's only in the Server role, the one that installs it. InstallerOwnership detects the product with MsiEnumRelatedProducts and reads the recorded role and environment (no recorded role counts as Workstation, the MSI's default). The tray app

Dev.Conduit.exe tray runs a Windows Forms ApplicationContext on an STA thread of its own, after letting go of the console: a console of its own is freed, and a terminal's is left by starting a detached copy. A named mutex per user and session keeps one instance; a second launch sets a named event the first waits on, and the first opens its setup window. Every three seconds the tray asks the service control manager whether Dev.Conduit is installed and picks its role:

  • Server role (ServerRole): polls the service's status and starts, stops and restarts it through the elevated helper; exports a client configuration (ClientConfigExportFlow, shared with the Server page); and uninstalls a service the MSI does not own (ServiceActions). Exit never touches the service.
  • Workstation role (WorkstationRole, LocalProxyHost): builds local mode with TryBuild(["--mode", "local"], runningAsService: false, ...) and drives StartAsync / StopAsync, building afresh on every start so saved settings apply. The token warmup runs inside StartAsync, which is the signing in state; the interactive MSAL sign-in works because the tray runs in the user's session. A refusal to start keeps the fatal problems for a notification and the log. The log sink is a ring buffer of the last 2,000 lines (LogRingBuffer), which the log window shows. The running application's ClientTrustStatusBoard is read on every poll: when a server's status reports UpdateNeeded (RootStoreUpdateNeeded or MachineIdentityRenewalDue) the tray shows one notification and an Update Dev.Conduit certificates (needs admin) item that runs service-admin trust for each such server and then asks the sync to run again. Without the MSI the menu also offers Install service. The tray starts local mode itself when it starts, and after a save or an import leaves it stopped, when LocalProxyAutoStart finds the configuration ready (a remote, no fatal problem, Entra ids to sign in with) and Start proxy automatically (DevConduit:Tray:AutoStart in the user file, on by default) is ticked. A failed start shows its status and one notification; it is not retried.

The setup window shows one set of pages per role, built from a SetupContext (role, settings files, helper, client folder, hosts file, the local proxy's sync results): a workstation gets Servers, Routes, Local proxy and About; a server gets Server, Routes and About. Nothing on any page concerns certificates, and a workstation never sees server settings. The pages are thin Windows Forms controls over plain model classes in Tray/Setup: SettingsLayers, RoutingEditModel (routes only; a route naming no server goes to the only one), LocalProxySettingsModel, ServerSettingsModel (host name, port, client address, Entra ids, scope, allowed users, groups and targets, and the warnings ServerExposureWarnings gives when they leave the server open), ImportedServerList with ServerTrustReader (the Servers rows and their certificate status in words), UserRoutesCleanup and ClientConfigExportPlan. The Routes page validates every edit with the real RoutingConfigurationParser.Parse and RouteAliasTable against the configuration the file would give once saved.

Saving one page never clears another. Each model's change set touches only the keys its page owns. After any save every page reloads from SettingsLayers: the page that saved takes the files as they are, and every other page calls its model's Reload, which reads the files again but keeps each field (or route row) edited since the model loaded: a changed row keeps its values, an added row stays, a deleted row stays deleted unless a lower file defines it, and untouched rows follow the files. Each save likewise rebases the page's model on the files as they are at that moment before computing its change set, so a save never writes from a stale snapshot. Before this, the window reloaded every page from the files after any save, which threw away what had been typed into the other pages and not yet saved.

Elevation. The tray never runs elevated. An administrative action starts the same exe with the runas verb as service-admin <action>: start, stop, restart, install <environment>, uninstall, save <transfer file> [<environment>], export, import, seed, trust <hostname>, forget <hostname>, revoke <serial> or untrust. The helper's exit code is its whole report (ServiceAdminExitCode), and a declined UAC prompt (ERROR_CANCELLED) is a silent no-op. Its targets are fixed: the service Dev.Conduit, and the machine settings file. For a save the unelevated side writes a SettingsChangeSet to a new file named Dev.Conduit-settings-<32 hex>.json in its temp folder; the helper reads only a file so named, refuses a reparse point or anything over 256 KB, refuses a change touching any key outside ManagedSettingKeys.Machine (exactly what the Server and Routes pages write), applies it with the protected access list, and deletes the transfer file. An import or removal is held to ManagedSettingKeys.Imported instead, and a seed to ManagedSettingKeys.Seed. Install runs the exe's own Topshelf install -environment:<name> in a child process (the tray passes Production); environment names are limited to letters, digits, ., - and _. trust and forget accept only a lower-case DNS host name.

The client credential in a published instance

On the VM, a published instance needs no secret at all. The managed identity credential in AzureAd:ClientCredentials is committed configuration — it names the UAMI's client id, which is not a secret — and works in any environment, provided the UAMI is attached to the VM. Off the VM there is no managed identity, the assertion cannot be obtained, and the client secret fallback is the only option.

For the secret fallback: user secrets do not load outside Development. The .NET host adds the user secrets configuration source only when the environment name is Development. A published instance started without DOTNET_ENVIRONMENT / ASPNETCORE_ENVIRONMENT set to Development therefore reads no secret at all, and sign-in fails with an invalid-client error that says nothing about configuration. Supply the secret another way: the environment variable AzureAd__ClientSecret (double underscore), or a key vault / configuration provider added to the host. Do not solve it by putting the secret into appsettings.json.

For development off the VM, the secret goes into user secrets: 

cd src\Proxylayer.DevConduit
dotnet user-secrets set "AzureAd:ClientSecret" "<the secret value>"

Startup logs the credential in use as Entra client credential: …. When the tenant and client ids are present but no credential is configured, it logs a warning naming both options rather than failing silently.

What is not covered

  • No end-to-end host tests. Nothing starts Kestrel, drives a real /route call, or asserts the middleware ordering that 01.1 depends on. The ordering decisions are enforced only by the comments in DevConduitApplication.
  • No authentication or authorization tests. RouteAuthorizer, BearerScopeGuard, DevConduitAuthorization and the OIDC post-configuration — including the response_mode=query decision this document calls load-bearing — have no coverage.
  • No MSAL or token-lifecycle tests. Acquisition order, the refresh skew, the acquisition semaphore and the cache-failure fallback are unverified.
  • No streaming or capture tests. CappedBuffer, CapturingReadStream and RoutedTrafficRecorder — including the queue-saturation drop behaviour — are exercised only indirectly.
  • No forward-proxy socket tests. Head parsing and target matching are covered; the tunnel, the keep-alive decision, the timeouts and the shutdown path are not.
  • No browser-side tests. wwwroot/app.js has no test coverage of any kind.
